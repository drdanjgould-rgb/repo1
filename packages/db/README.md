# @contourai/db

Drizzle schema + migrations + seed for ContourAI's Postgres database
(Supabase in prod).

## Layout

```
packages/db/
├── src/
│   ├── schema/         # one file per table; index.ts re-exports
│   ├── client.ts       # createClient(), setRequestContext()
│   ├── migrate.ts      # `db:migrate` entrypoint
│   ├── seed.ts         # `db:seed` entrypoint (idempotent)
│   └── index.ts        # public exports
├── drizzle/
│   ├── 0000_initial.sql            ← generated by drizzle-kit
│   ├── 0001_rls_and_audit.sql      ← hand-written
│   └── meta/                       ← drizzle journal + snapshots
├── test/
└── drizzle.config.ts
```

## Migrations

Two layers:

| Layer                              | How                    | Source of truth              |
| ---------------------------------- | ---------------------- | ---------------------------- |
| Table/column DDL                   | `drizzle-kit generate` | `src/schema/*.ts`            |
| RLS policies, triggers, invariants | Hand-written SQL       | The hand-written file itself |

Both file types live in `drizzle/`. The migrator runs them in journal order.

### Workflow

```bash
# 1. Edit schema under src/schema/
# 2. Generate the migration:
pnpm --filter @contourai/db db:generate

# 3. If you need RLS/trigger changes, hand-write a follow-up:
#    drizzle/000N_<description>.sql
#    Then add it to drizzle/meta/_journal.json and copy the prior snapshot
#    so drizzle-kit doesn't get confused on the next generate.

# 4. Apply:
DATABASE_URL=postgres://… pnpm --filter @contourai/db db:migrate

# 5. Seed (idempotent, dev only):
DATABASE_URL=postgres://… pnpm --filter @contourai/db db:seed
```

### Why both auto and hand-written

Drizzle-kit doesn't understand RLS policies, triggers, or functions. Forcing
them through code-gen produces brittle migrations that diff against an empty
snapshot every time. We let drizzle-kit own table/column DDL where it
excels, and hand-write the security layer where the SQL is the spec.

## RLS contract

Every read/write must run inside a transaction that sets:

```ts
await db.transaction(async (tx) => {
  await setRequestContext(tx, { clinicId, actor: 'user:<uuid>' });
  // …queries here are RLS-scoped to clinicId…
});
```

`setRequestContext` uses `SET LOCAL` semantics — settings expire on commit
or rollback. No leakage between transactions.

The Supabase `service_role` JWT bypasses RLS by default. Use it ONLY in
trusted server-side workers that are themselves the boundary; the API
layer always uses `authenticated`.

## Audit trail

`audit_log` is populated by a Postgres trigger function (`audit_trigger_fn`),
not by application code. Triggers are attached to: clinics, users, patients,
conversations, messages, leads, lead_scores. They write under
`SECURITY DEFINER` so they bypass RLS to write the audit row, but the rows
themselves are RLS-scoped by clinic_id for read.

App code MUST NOT INSERT into `audit_log` directly. RLS allows SELECT only
to the `authenticated` role.

## Encryption strategy

PHI columns are `bytea`. The application layer encrypts/decrypts via
libsodium (`@contourai/phi-redact` will own this) with a key fetched from
Supabase Vault at boot.

For equality lookup without decryption, we store SHA-256 hashes alongside
in `*_hash` columns. Use the hash for `WHERE email_hash = sha256(lower(email))`
queries; never query the encrypted column.

## Tests

`pnpm --filter @contourai/db test` runs schema smoke tests (no DB needed).
Live-DB tests (RLS enforcement, audit firing, denorm invariant) land in
`test/rls.test.ts` once a testcontainer/CI Postgres is wired.
